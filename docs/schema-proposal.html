The build order needs one correction

AccCloud-first is right. getProductRemain is the wrong endpoint for it, and building against that assumption would cost a sprint.

getProductRemain cannot produce a product master

It returns quantity on hand per product per warehouse — balances only. No unit, no conversion factor, no category, no barcode. Syncing it into an empty database gives you stock figures for products that have no records.

This is already settled work: onest-wms investigated the same API and recorded it as D-17, then received the owner's final spec as D-24. Both are in onest-wms/DECISIONS.md.

The item master needs two endpoints joined on prodCode:

  • ProductMaster1/getByProd — codes and names
  • Get Product By Warehouse — unit and conversion factor

getProductRemain then becomes step two: opening balances and ongoing reconciliation, once there are products to reconcile against.

Four constraints from D-24 shape the tables below, so they are worth stating here:

  • Auth is two headers, x-api-key and x-secret-key, with companyCode in the body. Success is status: "000".
  • No barcodes, from any endpoint. Barcode identity is ours to own, which promotes barcode capture from a detail to real scope.
  • 1000-row cap when searchAll='N'. A response of exactly 1000 must fail loudly — a silently truncated sync reporting "no variances" is worse than one that errors.
  • Field names verbatim, including the misspelled differnce. Correcting it in our code reads undefined at runtime and reports a zero variance.

Branches — settled and applied

Your canonical list is seven names, and UAT already held exactly those seven. There was no extra one to remove. Production is the database with extras: Head Office, Factory and Retail, seeded by schema.sql as organisational entries rather than shops.

006-canonical-branches.sql is written as an allowlist, so it produces the same end state in either database regardless of what each started with. It deactivates, never deletes — six tables reference branches with ON DELETE CASCADE, so deleting one would silently destroy that branch's entire sales history, stock levels and movement ledger.

Applied to UAT: seven active, zero stranded staff. It also adds a unique constraint on branches.name — without one, on conflict do nothing has no index to detect a conflict against, and re-running the file produced fourteen branches instead of seven.

Why a table, not a column on branches. AccCloud speaks in warehouse codes; the app speaks in branches. Every balance, receipt and reconciliation arrives keyed by whCode. A branch may map to more than one warehouse, and some warehouses map to none — a column cannot express either. Without this table every sync guesses the mapping, and a wrong guess puts a shop's stock in the wrong shop.

C · Stock

stock_levelsredesign

Keeps product_id, branch_id, quantity. Adds min_level and max_level — there is no max anywhere in the schema today, and minimum_override is renamed into the pair so the two read as one concept.

stock_counts + stock_count_linesnew
ColumnTypeNotes

statustextdraft → submitted → approved

system_qty / counted_qtyinteger

Explaining and approving are deliberately different people. stock.variance.explain belongs to ka alone; stock.adjustment.approve to admin and manager. The person who counted writes why it differs; someone else decides whether the ledger moves. Putting both on one row with one actor would collapse a control you have already specified.

stock_movementsredesign

Same shape, plus a trigger refusing UPDATE, DELETE and TRUNCATE.

A ledger you can edit is not a ledger. onest-wms enforces exactly this and it is the reason its demo database had to be retired rather than cleaned — worth knowing the cost, and worth paying it. The corollary: mistakes are corrected by a compensating movement, never by editing history, so the UI must offer that instead of a delete button.

stock_adjustmentsnew

Links an approved variance to the movement it produced: count_line_id, qty_delta, reason, requested_by, approved_by, approved_at, status.

The approval needs somewhere to live. Without it, "who authorised this write-off" is answerable only from an audit log, which is the wrong place for a business fact.

D · Movement documents

All three follow one header-and-lines shape, so the UI and the posting logic are written once.

receipts + receipt_linesnew

Inbound goods. Header carries branch_id, supplier_id, received_at, status, reference; lines carry product, expected and received quantity.

Capability receiving — admin, manager, supervisor, ka, logistics. Recording expected alongside received is what makes a short delivery visible rather than merely a small number.

transfers + transfer_linesnew

from_branch_id, to_branch_id, status (draft → sent → received), sent_at, received_at.

Stock in transit belongs to neither shop. A transfer that decrements the sender and increments the receiver in one step makes the goods teleport; anything lost between the two shops is then invisible. The three-state flow is what lets you ask how much is on a van right now.

deliveriesnew

Scheduled outbound runs: branch_id, scheduled_for, window, status, notes, optional link to a transfer.

Capability delivery.schedule — admin, manager, logistics.

F · People, time and pay

pay_ratesnew
ColumnTypeNotes
staff_iduuid → profiles
effective_fromdatehistory, not current value
monthly_salarynumeric
hourly_ratenumeric

A separate table for three reasons. It is personal data and must never be copied into UAT — easy to guarantee when it is one table, hard when it is four columns on profiles. It carries its own RLS, gated on payout.view. And it is dated, because recalculating last quarter's payroll needs the rate that applied then, not the rate now.

overtime_recordsnew

staff_id, branch_id, work_date, hours, multiplier, status, approved_by.

multiplier is stored, not computed at read time. Part-time staff get no OT multiplier, and that rule may change. Recording what was actually applied means a rule change does not silently rewrite last month's approved overtime.

commission_rules · commission_runs · commission_linesnew

Rules are dated. A run snapshots the period, the pool, and every participant. Lines hold each person's share.

The run must record its own denominator. Part-timers are excluded from the commission pool denominator — so who was counted is the single most auditable fact in the calculation, and the most likely thing to be disputed. If the denominator is recomputed from today's roster, a person joining or leaving retroactively changes a payout that has already been made.

profiles · work_schedules · leave_requests · training_*keep

All unchanged. profiles.employment_type stays the single source of part-time status, feeding both the OT multiplier and the commission denominator.

Open questions

Six of these are cheap to answer now and expensive to guess. The first two are inherited from D-24 and are settled by one real API response each.

  1. Is getProductRemain.masterId the same value as productMaster1Id? Both are headed for acccloud_master_id. If they differ, matching on that column creates duplicate products. The sync should assert they agree on first run and refuse to commit if not.
  2. What is prodConvFactor relative to? A bare factor with no stated base. Inverted, a drum-to-kilo conversion is wrong by 200×.
  3. Do read-only AccCloud credentials exist for UAT? You asked for the sync to run against UAT so the integration gets tested. That needs a separate key pair — a reset invalidates the old one immediately, so it cannot be the production pair.
  4. Which whCode maps to which branch? I have no list. This is the one piece of master data that cannot be derived from anything already in the repo.
  5. Which nationalities are counted on bills? Determines the seed list, not the schema.
  6. Should shop_traffic move to rows like bills? It is empty, so this is free now and a migration later.
  7. Can a branch have more than one warehouse? The proposed table allows it. If the answer is always one, a unique constraint on branch_id makes that explicit.

Build order

Numbered because the order genuinely constrains: each phase needs the one before it to have produced rows.

01

AccCloud item master

Both endpoints, joined on prodCode. Paging, the 1000-row guard, and the two assertions from Q1 and Q2 on first run.

warehouses · products · product_uoms · erp_sync_runs · erp_import_rows

02

Balances and reconciliation

getProductRemain — now that there are products to match against. Opening balances, then a recurring variance report.

stock_levels · stock_movements

03

Counting, variance, adjustment

The first screen shop staff touch. Exercises the ka-explains / manager-approves split end to end.

stock_counts · stock_count_lines · stock_adjustments · product_barcodes

04

Receiving and transfers

Needs barcodes from 03 to be scannable, and in-transit state to be meaningful.

receipts · transfers · deliveries

05

Daily numbers

Sales, bills, POS money, traffic. Independent of stock, so it can run in parallel with 03–04 if there is capacity.

bills · sales_records · pos_money_records · shop_traffic

06

Time and pay

Last because it is the only domain holding personal data, and the only one where a bug costs someone their wages.

overtime_records · pay_rates · commission_rules · commission_runs · commission_lines
